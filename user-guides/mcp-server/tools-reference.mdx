The MSPortal MCP server exposes **232 tools** across **30 modules**. An AI assistant only ever sees the tools that your granted [scopes](/user-guides/mcp-server/index#what-an-assistant-can-do) and MSPortal permissions allow, so the working set is a subset of the list below.

<Info>
**Access column:** *Read* tools never change data. *Write (confirm)* tools return a confirmation step before anything is committed, so the assistant tells you what it is about to do first. *Write* tools run immediately; their descriptions explain whether they make a low-risk, self-scoped change or generate a result without saving data.
</Info>

## Core

**Scopes:** `companies.read`, `companies.write`, `goals.read`, `planner.read`, `reports.read`, `tickets.read`

| Tool | Access | Description |
|------|--------|-------------|
| `get_company` | Read | Get one company by ID, including its custom field values (label → value). |
| `get_company_defaults` | Read | Get one company's defaults: hardware/software standards, workplace and security defaults, ticket defaults, onboarding checklist, and the AI-context fields that feed the AI assistant and new-ticket generation. |
| `get_current_user` | Read | Return the connected MSPortal user, tenant, user type, company, and OAuth grant summary. |
| `list_companies` | Read | List companies visible to the connected user. |
| `list_company_account_notes` | Read | List synced Autotask account/company notes for one company, newest activity first. |
| `search_portal` | Read | Search across visible companies, tickets, goals, planner items, and reports with small capped result sets. |
| `submit_feedback` | Read | Send product feedback to the MSPortal team. Use this whenever the user asks for something the MCP server cannot do (a missing tool, capability, or data set), or wants to report a bug or suggestion. Summarize what the user was trying to accomplish in the message. |
| `update_company_defaults` | Write (confirm) | Stage or apply a partial update to one company's defaults (standards, workplace/security defaults, ticket defaults, AI context). Only the provided fields change; null clears a field. |

## Compliance

**Scopes:** `compliance.read`, `compliance.write`

<Note>
MSPortal uses two related kinds of template. A **check definition** is one reusable compliance check; `list_compliance_templates` is a backward-compatible alias for `list_compliance_check_definitions`. A **run template** is a reusable bundle of groups and individual check definitions. Use the `*_compliance_run_template` tools when you want to manage those bundles.
</Note>

| Tool | Access | Description |
|------|--------|-------------|
| `get_compliance_company_summary` | Read | Get authoritative active-run totals and scores by company, including tie-aware portfolio leaders. |
| `get_compliance_check` | Read | Get one assigned compliance check. |
| `get_compliance_check_definition` | Read | Get one base check definition with its instructions, rationale, remediation, references, scope, priority, approval state, and exact group membership. |
| `get_compliance_group` | Read | Get one compliance group with its exact check membership. Use this before replacing a group's checks. |
| `get_compliance_risk` | Read | Get one compliance-derived risk with its occurrences, source state, remediation work, standards references, and audit history. |
| `get_compliance_risk_gap` | Read | Get one failed-check gap that is eligible for promotion to the risk register or dismissal. |
| `get_compliance_run` | Read | Get a compliance run with assigned checks. |
| `get_compliance_run_template` | Read | Get one reusable run template with the exact groups and individual checks it assigns. |
| `list_compliance_check_definitions` | Read | List base check definitions. Use these IDs as `checkIds`; they are not run-template IDs. |
| `list_compliance_checks` | Read | List assigned compliance checks. |
| `list_compliance_groups` | Read | List compliance groups with their type, auto-map setting, and check count. |
| `list_compliance_risk_categories` | Read | List active risk categories for creating or recategorizing compliance-derived risks. |
| `list_compliance_risk_gaps` | Read | List the latest failed compliance results eligible for risk promotion or dismissal. |
| `list_compliance_risks` | Read | List compliance-derived risks with company, status, category, severity, owner, and target-date filters. |
| `list_compliance_run_templates` | Read | List reusable run templates. Pass these IDs as `templateIds` to `create_compliance_run`. |
| `list_compliance_runs` | Read | List compliance runs. |
| `list_compliance_status_options` | Read | List the valid status options for an assigned compliance check. Use the returned id as statusItemId with update_compliance_status. |
| `list_compliance_templates` | Read | Backward-compatible alias for `list_compliance_check_definitions`. |
| `create_compliance_group` | Write (confirm) | Stage or create a tenant-wide compliance group, optionally with an exact set of check definitions. |
| `create_compliance_risk` | Write (confirm) | Stage or promote one eligible failed-check gap into the risk register. This does not create an unrelated standalone risk. |
| `create_compliance_run` | Write (confirm) | Stage or create compliance runs, one per company, and enqueue checks from run templates, groups, and/or individual check definitions. At least one source is required. |
| `create_compliance_run_template` | Write (confirm) | Stage or create a reusable run template with exact group and individual-check membership. |
| `create_compliance_template` | Write (confirm) | Stage or create a base compliance check definition. New definitions start in pending review; optional `groupIds` set exact group membership. |
| `delete_compliance_group` | Write (confirm) | Stage or permanently delete a group. Check, device-type, and run-template mappings are removed; historical assignments keep their check but lose the group link. |
| `delete_compliance_run_template` | Write (confirm) | Stage or permanently delete a reusable run template, including its memberships and schedules. |
| `delete_compliance_template` | Write (confirm) | Stage or permanently delete a base check definition and its assigned checks, history, group mappings, run-template memberships, and completed-meeting links. |
| `dismiss_compliance_risk_gap` | Write (confirm) | Stage or dismiss one eligible failed-check gap with a reason. A later failed run can create a new gap. |
| `draft_compliance_notes` | Write | Generate sanitized public-note drafts from private-note answers without saving them. Review the result, then use `update_compliance_checks` to stage the notes. |
| `update_compliance_check` | Write (confirm) | Stage or update one assigned check's status, notes, priority, flag, or due date. |
| `update_compliance_checks` | Write (confirm) | Stage or update one to 25 assigned checks in one operation. |
| `update_compliance_group` | Write (confirm) | Stage or update a group's editable fields. Supplying `checkIds` replaces its exact membership; an empty array clears it. |
| `update_compliance_risk` | Write (confirm) | Stage or update a non-closed risk's assessment, status, owner, treatment, target date, category, or client visibility. |
| `update_compliance_run` | Write (confirm) | Stage or update a run's name, notes, run date, or completion state. |
| `update_compliance_run_template` | Write (confirm) | Stage or update a reusable run template. Supplied `groupIds` and `checkIds` each replace that exact membership. |
| `update_compliance_status` | Write (confirm) | Backward-compatible assigned-check update tool for status, notes, and priority. |
| `update_compliance_template` | Write (confirm) | Stage or update a base check definition. Only supplied fields change; null clears nullable fields and `groupIds` replaces exact membership. |

<Warning>
Compliance catalog writes are available only to internal MSPortal users. Creating and updating groups, check definitions, and run templates requires **Write Compliance** or **Manage Compliance**; deleting them requires **Manage Compliance**. Deletions are permanent and their confirmation preview calls out the affected mappings, schedules, assignments, or history.
</Warning>

## Notes

- **Scopes vs permissions.** A scope is what the AI client asks for at connect time; a permission is what your MSPortal role grants. A tool runs only when *both* allow it. Company (client-portal) users are additionally restricted to their own company's data and have sensitive fields redacted.
- **Confirmation flow.** Tools marked *Write (confirm)* return a proposal first. Your client surfaces what will change, and the write commits only after you approve.
- This list reflects the current release and grows over time. The live set your assistant can use is always discoverable from the client itself (for example `/mcp` in Claude Code).
